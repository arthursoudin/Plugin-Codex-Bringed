# Roadmap por fases

Este documento registra o estado observável no repositório em 2026-10-26. "Implementado no código" não significa que foi instalado ou validado na máquina de destino, conectado a uma conta externa ou publicado.

## Fase 1 — Núcleo CodexBridge local

Relatórios Codex mantêm `durationMs` e podem incluir `latency_ms` com tempos em milissegundos: `tool_received_to_runner_start`, `spawn_call`, `spawn_confirmed`, `first_jsonl_data`, `process_end` e `response_extraction`. Valores indisponíveis são `null`. As métricas registram apenas durações, sem conteúdo de prompt ou resposta. Baseline local de 2026-10-26: `codex --version` levou 1.091 ms na primeira chamada e mediana de 530 ms em três chamadas aquecidas; `codex_status` pelo MCP levou mediana de 622 ms em três chamadas. São operações diferentes, então essa diferença não mede isoladamente o túnel. Para o Hermes, o mesmo `hermes --version` teve mediana de 2.947 ms em três spawns locais e 3.495 ms em três chamadas `hermes_status` pelo MCP no ensaio inicial de três pares. Um segundo ensaio, com cinco pares, mediu medianas de 2.626 ms local e 2.590 ms pelo MCP (diferença de -36 ms), mas com variação alta entre amostras. Em mais oito pares, as medianas foram 2.904 ms local e 2.418 ms pelo MCP; uma das chamadas MCP levou 4.164 ms. Os resultados curtos variam e não demonstram que o MCP seja mais rápido nem que tenha sobrecarga persistente. Foi implementado cache de 30 segundos, apenas para respostas concluídas, compartilhado por `hermes_status` e `hermes_environment_check`; falhas e timeouts não são cacheados. Chamadas simultâneas também compartilham o mesmo spawn. A resposta informa se usou cache ou aguardou a mesma execução, a idade e a duração. Testes confirmam reutilização, compartilhamento concorrente e nova tentativa após timeout. A instalação MCP ativa ainda não apresenta os novos campos de cache, portanto a otimização do fonte ainda não foi validada nela; percentis maiores e validação após migração ainda faltam.

**Estado: implementada no repositório; validação descrita nos documentos de origem.**

O pacote contém o núcleo em `bridge/`, integração com Codex CLI, fluxo de preparação e aprovação local de uso único, execução e consulta de tarefas, relatórios e testes do núcleo. O modelo mantém um projeto autorizado por processo e usa o sandbox configurado pelo executor. Os documentos legados descrevem validações locais anteriores, mas elas não demonstram o estado atual de uma instalação ativa nesta pasta.

## Fase 5 — Economia de tokens e MCPs complementares
**Estado: integração local sob demanda de RTK e Headroom e registro opcional do MCP Headroom no Codex após consentimento implementados. RTK foi validado com armazenamento temporário; validação com ledger Headroom real continua pendente.**

Quando RTK é selecionado nas preferências de Economia de tokens, o dashboard oferece uma ação explícita que executa `rtk gain --all --format json`, valida e importa apenas a série diária, com deduplicação. A chamada usa argumentos fixos, sem shell, timeout e limite de saída. Não executa ao abrir o dashboard, não lê o banco SQLite e não envia dados pela rede. Os tokens são estimativas da saída de shell (`bytes / 4`), não uma medição de cobrança. Quando Headroom é selecionado, uma ação explícita lê e valida o ledger local `savings_events.jsonl`, limitado a 1 MB, e deduplica eventos; não executa comandos nem altera o ledger. Em 2026-10-26, `headroom savings --json` retornou zero chamadas/economia e o arquivo padrão não existia; validar a importação com eventos reais continua pendente. Graphify oferece pesquisa da arquitetura do código e não é um medidor de economia. Nenhuma dessas ferramentas é requisito para as funções principais do CodexBridge.

Nesta fase, o painel explica o papel de RTK, Headroom e Graphify antes da configuração. Graphify tem uma ação opcional, protegida por confirmação, que instala o CLI oficial se ausente e registra a integração no perfil Codex do usuário; essa ação não cria um grafo de projeto nem salva chaves. RTK e Headroom também têm instaladores guiados, cada um com confirmação explícita: RTK usa o pacote oficial do winget sem editar configurações do Codex; Headroom usa `uv` e Python 3.13 em ambiente isolado. A instalação Headroom pode depender de ferramentas de compilação no Windows. Nenhuma das ações captura chaves de API ou configura conexões de provedor automaticamente.
Após selecionar e instalar Headroom, a página Economia de tokens pode registrar o MCP oficial no Codex com aceite explícito. Usa o caminho absoluto do executável com `codex mcp add headroom -- <executável> mcp serve`, confere a configuração atual e não substitui uma entrada existente. Isso habilita as ferramentas Headroom em sessões futuras, mas não configura o proxy nem torna a compressão automática. Para gerar eventos, o agente precisa chamar `headroom_compress` ou o proxy deve processar tráfego; o ledger padrão não foi encontrado neste computador nesta etapa.

## Fase 6 — APIs externas e conectores
**Estado: criação local de servidor HTTPS no Codex CLI após consentimento e teste individual do MCP Hermes com consentimento implementados; conexões externas, autenticação e instalação de servidores continuam pendentes de configuração/validação.**

O configurador (`codex_mcp_configurator`) prepara instruções para ChatGPT, Codex CLI, Hermes CLI, Gemini CLI e OpenCode CLI. A pessoa pode escolher os destinos; se não indicar nenhum, o retorno contém os quatro roteiros de CLI. O painel `/dashboard/mcps` funciona sem projeto, valida os campos, apresenta comandos ou trechos de configuração, guarda um registro local e permite anotar o progresso por destino. Essa anotação é manual e não prova uma conexão. OAuth é concluído no próprio cliente. O valor literal de uma chave nunca é aceito em argumentos nem persistido; para clientes com suporte documentado, são geradas apenas referências ao nome de variável de ambiente. As configurações e autenticações de cada cliente são independentes. O configurador não altera configurações externas, não executa os comandos, não instala servidores e não conclui OAuth. Stdio local não conecta diretamente ao ChatGPT; é necessária outra conexão HTTP remota ou tunnel para esse destino. Não há evidência de que APIs externas tenham sido conectadas ou de que a autenticação e permissões de uma conta tenham sido concluídas.

O formulário **Adicionar servidor ao Codex** é uma exceção explícita aos roteiros: após o usuário informar nome, descrição local, URL HTTPS do endpoint (inclusive URL entregue por tunnel), método de autenticação e aceitar a confirmação de confiança, o painel executa `codex mcp add` no perfil global do usuário. A descrição fica no histórico local, pois o Codex CLI não oferece esse campo. OAuth e bearer token continuam exigindo configuração separada pelo usuário; o valor do segredo nunca entra no formulário. O formulário não autentica nem testa a conectividade de rede do endpoint.

Teste de regressão acrescentado em 2026-10-27 para esse fluxo com CLI falsa e `CODEX_HOME` temporário: valida bloqueio sem aceite, argumentos esperados para URL/tunnel e referência de bearer por variável de ambiente, histórico local da descrição e recusa de nome duplicado. Nenhuma configuração Codex pessoal foi alterada. A suíte passou com 69/69, typecheck passou e `package:check` validou 24 arquivos sem gerar ZIP.

Depois do comando de criação e sob demanda pelo botão **Conferir registro local**, o painel consulta `codex mcp list`, guarda resultado e horário, e distingue encontrado, não encontrado e falha na consulta. Esse indicador é apenas de configuração local: não declara que HTTPS/tunnel está acessível nem que a autenticação foi concluída.

Os roteiros salvos podem conferir registro local do Codex e Hermes pelo comando `mcp list`, e do Gemini pela leitura somente da configuração JSON global do usuário. O resultado guarda apenas estado e horário, sem saída bruta ou valores de segredo. OpenCode continua manual, pois os arquivos JSONC podem ser globais ou de projeto e seu comando `mcp list` apresenta estado de conexão; o adapter não inicia esse comando automaticamente. A consulta local não prova conexão. Para Hermes, a dashboard também oferece um teste individual após confirmação explícita: só o mostra quando `hermes mcp list` encontra o nome e o handler repete essa checagem antes de chamar `hermes mcp test <nome>`. O painel armazena somente resultado categorizado e horário, nunca a saída. Sucesso confirma uma interação MCP naquele instante; falha não identifica a causa. Esse teste não adiciona nem modifica a configuração do Hermes.

O roteiro de autenticação por chave agora recebe somente o nome da variável de ambiente e, opcionalmente, o nome do cabeçalho. Valida o formato e persiste esses identificadores, nunca o valor secreto. Codex gera `--bearer-token-env-var` para URL remota com cabeçalho Authorization; Hermes gera referência `${env:VAR}`; OpenCode usa `{env:VAR}`; Gemini só gera referência segura em `env` para servidor stdio. Para cabeçalhos HTTP no Gemini e combinações sem suporte documentado, não gera comando com segredo: informa a limitação e pede configuração pelo mecanismo oficial do cliente. Os snippets continuam manuais e não alteram arquivos de configuração.

Na checagem local de 2026-10-26, os executáveis `codex`, `hermes`, `gemini` e `opencode` foram encontrados no `PATH`; as versões locais são Codex 0.164.0, Hermes 0.21.5, Gemini 0.64.0 e OpenCode 2.0.32. A saída de `mcp add --help` foi confirmada diretamente nos quatro clientes: Codex oferece `--bearer-token-env-var` apenas para HTTP; Hermes separa `--env` stdio e `--auth {oauth,header}`; Gemini oferece `--env` e `--header`; OpenCode oferece `--env` local e `--header` remoto. Uma verificação isolada gerou e interpretou os snippets com a variável fictícia `TEST_MCP_TOKEN`: formatos Codex/Hermes/Gemini stdio/OpenCode passaram; Gemini HTTP sem expansão documentada foi bloqueado; valor com formato reconhecível de segredo foi rejeitado. Nenhuma configuração foi alterada, conexão MCP feita ou segredo real usado. A verificação isolada não comprova a interpretação dos snippets pelo runtime de cada cliente.

Validação dos parsers locais concluída em 2026-10-26: o loader de configuração Hermes do runtime instalado carregou o snippet gerado numa `HERMES_HOME` temporária, aceitou URL/cabeçalho e expandiu `TEST_MCP_TOKEN` para um marcador fictício; o `ConfigSchema.safeParse` do Gemini CLI 0.64 aceitou o JSON gerado e a referência de ambiente; `opencode debug config` já havia aceitado seu snippet gerado. Nenhum MCP foi iniciado nem conectado; nenhum perfil pessoal foi modificado. A tentativa de `mcp list` continua inadequada como parser-only check porque inicia bootstrap ou discovery.

Também foi validado o parser do Codex CLI 0.164.0 usando `CODEX_HOME` temporário: `codex mcp add` e `codex mcp list` aceitaram uma URL fictícia HTTPS e a variável `TEST_MCP_TOKEN`. A validação de parsing dos quatro CLIs está concluída; ela não prova que qualquer endpoint externo esteja acessível ou autenticado.

Melhoria de jornada em 2026-10-26: quando `/dashboard/impact` não tem dados no período, o painel agora oferece atalhos diretos para importar relatório RTK/Headroom e registrar comparação manual, além de explicar como associar dados a um projeto. Os botões secundários são consistentes nos temas escuro e claro.
